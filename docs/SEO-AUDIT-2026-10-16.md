# ColorBase search visibility and product review

Reviewed on October 16, 2026. Scope: live HTTP responses, the production sitemap,
repository history, metadata, desktop and mobile screenshots, and browser errors.
This is a sampled audit, not a crawl of every page. Search Console, real-user Core
Web Vitals, server history, and deployment timestamps were not available.

The owner reports fewer Google clicks and impressions. The exact start date and
affected queries/pages are not yet established. The findings below identify
credible mechanisms and improvements; they do not establish a Google penalty or
prove which change caused the decline.

## Highest-priority investigation: retired tools

Commit `fd04397`, dated October 6, introduced 85 retired tool slugs and permanent
redirects to `/tools`. Live checks confirm `/json-formatter` returns HTTP 308 to
`/tools`; `/word-counter` and `/qr-code-generator` also resolve there. The
destination offers color tools rather than the requested functionality.

If those retired pages earned impressions, removing their functionality can
directly explain lost searches. An unrelated directory is a poor replacement
and may be treated as a soft 404. This does not imply the remaining color pages
have been penalized. The commit date is not a verified deployment date.

Recommended action:

- Compare Search Console performance for the retired URLs before and after the
  actual deployment. Separate their losses from losses on surviving color pages.
- Restore only useful tools that had traffic, links, or a deliberate product role.
- Redirect moved pages to equivalent functionality when that exists. For a
  deliberately removed page without a replacement, return a helpful 404 or 410.
- Do not restore all 85 tools or change every redirect without this comparison.

[Google: handling removed pages and soft 404s](https://developers.google.com/search/docs/crawling-indexing/troubleshoot-crawling-errors)

## Changes that would make users more likely to return

1. **Let people do something immediately.** At 390 × 844, the homepage hero occupies
   roughly the first 700 pixels; usable swatches begin near the bottom. Use a
   clearer heading such as “Free color picker, palettes, and contrast checker,”
   then offer a small editable HEX input with preview, conversion, and copy.
   Keep the existing search, but give the page one obvious starting action.
2. **Connect the existing tools into a workflow.** Carry the selected color or
   palette from picker to palette editor, contrast check, and CSS/Tailwind export.
   Shareable palette URLs and local favorites already exist; make them prominent
   rather than building another collection of disconnected tools.
3. **Replace seeded popularity counts.** `src/lib/palettes/likes.ts` derives
   30–2,000 apparent likes from each palette ID, then adds the current user's
   local preference. The library discloses seeded counts in introductory copy,
   but individual cards can still look like real community totals. Use “Save”
   without a public count, or show actual aggregate counts. This is a trust
   problem, not evidence of a specific Google ranking penalty.
4. **Make accessibility claims specific.** The palette score counts pairs with
   contrast at least 3:1. It is not a general WCAG certification for text. Show
   foreground/background pairs with AA normal-text, AA large-text, and AAA labels,
   plus previews. Keep the existing caveat, but make the card label precise.
5. **Add examples people can reuse.** Create a small set of carefully built themes
   for dashboards, portfolios, and landing pages, with real component previews,
   light/dark tokens, and a complete export. Publish tutorials that demonstrate
   those themes and link directly to their editable tools.
6. **Simplify distractions and establish ownership.** Collapse the desktop social
   rail initially and keep it from covering controls on phones. Verify that
   every linked social profile belongs to this project. Add named authors,
   correction methods, source links for brand colors, and meaningful review dates.
7. **Distribute useful examples.** Share short picker/contrast demonstrations and
   free theme examples in relevant developer and design communities. Use the
   example as the reason to visit. Measure actual use before investing in paid
   acquisition or many additional features.

Track `color_copied`, `palette_saved`, `palette_shared`, `export_downloaded`,
searches with no results, and returning engaged users. Avoid putting raw search
text, email addresses, or other personal data into event parameters. Evaluate
whether each design change increases successful tool use, not only page views.

## What worked in this review

- Primary sampled tool pages returned HTTP 200 with indexable metadata and correct
  self-canonical URLs. Main content was present in the server response.
- `robots.txt` allows public pages. The sitemap has no duplicate URLs.
- Desktop home, mobile home, and mobile picker showed no uncaught JavaScript
  exceptions. Both mobile views fit the 390-pixel viewport without horizontal
  overflow.
- A single unthrottled browser observation measured home LCP at about 0.97 seconds
  on desktop and 1.24 seconds with mobile emulation. These are diagnostic
  observations from this computer, not PageSpeed scores or real-user Core Web
  Vitals, and cannot establish search performance. Cache state differs between
  observations. Search Console's field data is still needed.
- The desktop home loaded 109 resources in the observation. Reducing optional
  animation, prefetching, and third-party work is worth testing, but there is no
  evidence here of a catastrophic loading failure causing the traffic drop.
- The earlier live Analytics check successfully sent page views. AdSense review
  status and an Analytics dashboard delay do not establish a Search ranking cause.

## Data needed to establish the cause

Do not share a Google password or recovery code. Windsor.ai was suggested as a
possible authenticated Search Console data connection; it is not confirmed
installed or connected. CSV/Excel exports and report screenshots are an alternative.

Collect:

1. Performance → Search results: the last three months, with clicks, impressions,
   CTR, and average position. Export Dates, Pages, Queries, Countries, and Devices.
   Compare the latest seven complete days against the previous seven, then
   examine dates around October 6 and October 14. Treat recent incomplete data
   separately. Include the exact date the owner first noticed the decline.
2. Page indexing: indexed/not-indexed trends and example URLs for the largest new
   exclusion reasons, particularly redirects, soft 404s, duplicate canonicals,
   crawled-not-indexed, and server errors.
3. Sitemaps: submitted sitemap URLs, last successful reads, and errors. Also check
   Manual actions, Security issues, Crawl stats, and mobile Core Web Vitals.

Interpretation:

- Loss concentrated on retired tools supports a removal/migration explanation.
- Broad position drops on surviving pages require checking indexing, deployment
  failures, relevance, competitors, and ranking changes.
- Stable positions with lower impressions can reflect lower demand or changes in
  query coverage; this is different from losing position for the same queries.
- Stable impressions with fewer clicks points toward CTR/search appearance issues.

The Search Status Dashboard showed no listed incidents for October 9–16 at the
time checked. That does not rule out smaller ranking changes or a site-specific
issue. Follow
[Google's traffic-drop investigation process](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops)
before attributing the decline to an algorithm update.

## Suggested order

First establish the lost pages/queries and update obsolete sitemap submissions.
Then resolve affected retired URLs and demonstrably redundant landing pages.
Next improve the most useful landing pages, remove misleading popularity counts,
and shorten the path from arrival to copying/exporting a color. Measure each
release and avoid changing every URL, title, and indexability rule at once.

This review makes recommendations only. No application behavior, redirects,
indexability settings, production deployment, or account configuration was changed.

## Implementation follow-up — October 17, 2026

After the review, the owner authorized useful changes. The local implementation now:

- Gives the homepage a live HEX preview, HEX/RGB copy actions, and links that carry
  the selected color into the picker, contrast checker, and palette generator.
- Uses clearer homepage copy and metadata, and a static hero background.
- Preserves a library palette's full color selection when opening its editor.
- Replaces seeded public like counts with personal Save/Saved controls, retaining
  existing local favorites. Save failures are reported rather than shown as success.
- Labels the 3:1 pair percentage accurately and adds per-pair AA/AAA contrast results.
  Pass/fail now uses the unrounded ratio, fixing false passes near WCAG thresholds.
- Keeps social controls collapsed on desktop and places mobile profile links in
  the footer so they do not overlap working controls.
- Redirects the five legacy sitemap paths to the current sitemap, omits unknown
  modification dates, and excludes internal search results from indexing and the sitemap.

Retired tool redirects and other existing landing-page URLs remain unchanged
pending Search Console evidence. This follow-up has not been pushed or deployed.

Validation: 25 automated tests, TypeScript, and the production build pass. Lint
reports zero errors and six pre-existing warnings. Browser checks on the production
build cover 320px/390px phone layouts, desktop layout, live copying, invalid input,
color and full-palette handoffs, saved-state persistence after a full reload, the
contrast table, all five legacy sitemap redirects, and search-result robots tags.
No uncaught browser exceptions were observed in those checks.
